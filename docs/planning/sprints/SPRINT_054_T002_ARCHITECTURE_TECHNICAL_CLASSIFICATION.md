# Sprint 054 T002 — `ARCHITECTURE_TECHNICAL.md` Section Classification

## Methodology and scope

This artifact is the read-only classification output required by Sprint 054
T002 (`docs/planning/sprints/SPRINT_054.md`), applying the same four-way
classification framework as T001 (CURRENT / FUTURE / MIXED / AMBIGUOUS,
established by `docs/historical/REPO_WORKFLOW_DOCS_AUDIT.md` Phase 6b) to
every major section and numbered subsection of
`docs/vision/ARCHITECTURE_TECHNICAL.md` (2,459 lines, read in full across six
passes: lines 1–400, 400–800, 800–1200, 1200–1600, 1600–2000, 2000–2459).

For each section, classification was based on:
1. the section's own framing language (normative "must"/"should"/"suggested"
   vs. descriptive claims naming concrete types, fields or directories), and
2. a targeted code/test verification pass — `docs/reference/MODULE_MAP.md`
   (the current package map) plus `Grep`/`ls` against
   `src/trading_framework/` for the concrete classes, protocols, enums,
   package directories, or fields the section names (e.g. `ExecutionMode`,
   `DatasetLifecycleState`, `ComponentRequest`, `MarketFieldReference`,
   `Clock`, `EventBus`, `SignalOccurrence`, `AnalysisContext`,
   `reproducibility_status`).

Per **D-S054-02**, sections that could not be confidently classified from a
reasonable amount of reading + grep/ls-level verification are marked
**AMBIGUOUS** rather than guessed as CURRENT. No content in
`ARCHITECTURE_TECHNICAL.md` was moved, edited, or rewritten to produce this
table; the actual move (if any) is T004, gated on this classification being
reviewed.

Purpose/header-only subsections that describe the document or a section
group rather than a system behavior (e.g. §1, §2.1, §3.1, §4.1, §5.1, §9.1,
§10.1's own framing line) are noted as **N/A (meta)** rather than forced
into the four-way scheme, matching T001's precedent.

## Notable structural finding used throughout

`ARCHITECTURE_TECHNICAL.md`'s proposed package layout (§10) is written as a
**suggestion** ("Initial minimal structure", "Possible later structure",
"Suggested internal capabilities") rather than an as-built description, and
the actual `src/trading_framework/` layout has diverged from it in a
consistent, structural way: several concepts the vision nests under other
domains (`model_expression/`, `model_authoring/`, `market_model/`,
`signal_model/`) are separate top-level packages in code (per
`docs/reference/MODULE_MAP.md` §2), and the `events/` and `api/` packages
described in §8/§10.10/§10.14 are either an empty stub (`events/__init__.py`
is a one-line docstring with no `Event`/`EventBus` implementation) or do not
exist at all (no `src/trading_framework/api/`). This single finding drives
most of the MIXED/FUTURE classifications in §8 and §10 below — it is a
structural divergence, not a per-sentence one, so it is not re-derived line
by line for every subsection that shares it.

## Notable findings

- **The Event System (§8) is the single largest fully-FUTURE block in this
  document.** `src/trading_framework/events/__init__.py` contains only a
  one-line docstring — no `Event`, `EventBus`, handler, or command
  implementation exists anywhere in `src/trading_framework/`. Every named
  type in §8.2 (`MarketBarReceived`, `SignalGenerated`, `OrderSubmitted`,
  etc.) and every named implementation in §8.6 (`InMemoryEventBus`,
  `AsyncEventBus`, `RedisEventBus`) returned zero matches. This is a bigger,
  cleaner FUTURE block than anything found in T001's classification of
  `ARCHITECTURE_FOUNDATIONS.md` (which found no purely-FUTURE section at
  all) — T002 does have one, and it is unambiguous.
- **Replay and Live Execution remain unbuilt, consistently with T001's
  independent finding.** `execution/modes.py` supports only `DRY_RUN`
  (`SUPPORTED_EXECUTION_MODES = frozenset({ExecutionMode.DRY_RUN})`). This
  drives FUTURE classifications across §3.15 (Live Ingestion), §3.16
  (Replay), §2.8's `ReplayClock`/`ResearchClock` (MIXED), and §7.3 (Strategy
  Execution Modes) — the same underlying gap T001 found in
  `ARCHITECTURE_FOUNDATIONS.md` §6.5/§9 item 4, now confirmed independently
  from this document's own technical-contract angle.
- **§10 Module Structure is pervasively MIXED, not because the architecture
  is unbuilt, but because the actual package layout has structurally
  diverged from this document's suggested layout.** `model_expression/`,
  `model_authoring/`, `market_model/`, and `signal_model/` are separate
  top-level packages in code, not nested under `strategy/` as §10.7
  suggests; `research/` has gained `predictive/`, `robustness/`, `context/`,
  `observations/`, `outcomes/` (Predictive and Robustness Research postdate
  this vision text); and several suggested subdirectories simply don't exist
  (`time/calendars/`, `time/rolls/`, `market/requests/`,
  `market/services/`, `infrastructure/{brokers,cache,messaging}/`,
  `core/{enums,protocols,result}/`). None of this contradicts the document's
  *principles* (dependency direction, domain ownership) — those remain
  independently CURRENT per §5–§7 — but a literal section-to-directory move
  in T004 would need to reconcile this document's suggested tree with
  `docs/reference/MODULE_MAP.md`'s already-authoritative actual tree, not
  just relocate this document's text as written.
- **The promotion/fingerprint lifecycle (`reproducibility_status =
  EXPERIMENTAL`) is unbuilt here too, mirroring T001's finding for
  `ARCHITECTURE_FOUNDATIONS.md` §4.12.** Both the Market Analysis component
  version (§5.12) and the Model version (§6.4) of this same requirement
  return zero matches for `reproducibility_status`/`EXPERIMENTAL` anywhere
  in `src/trading_framework/`, while the underlying identity primitives
  (`component_id`, hash-based identity) these fingerprints would extend are
  pervasively implemented. This is the same genuine sub-section-level split
  T001 flagged — not a new finding, but an independent confirmation from a
  second document.
- **Configuration (§9) is more aspirational than its "Purpose" framing
  suggests.** Only a single-layer, single-file TOML loader
  (`config/loader.py`) with Pydantic schema validation exists; the layered
  precedence model (§9.4: Framework Defaults → Environment → User →
  Run-Specific Overrides) and per-run persisted resolved-configuration
  guarantee (§9.10) are not implemented as a general framework capability,
  though narrower, workflow-specific versions of "record what a run used"
  already exist (e.g. Predictive Research's dataset/run envelopes).
