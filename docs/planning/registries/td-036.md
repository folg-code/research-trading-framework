## TD-036 — `definition_hash` Is Not Comparable Across the `schema_version` Introduction

```text
Status: ACCEPTED
Priority: LOW
Domain: research/signal_research (definition.py)
Introduced: Sprint 064 T001 (2026-09-14), per ADR-0038 §2
Target Review: If an operator or tool is observed comparing a
  pre-Sprint-064 definition_hash against a current one and treating a
  mismatch as a real configuration change
Owner: Unassigned
```

### Accepted Shortcut

`SignalResearchDefinitionSpec` gained an explicit `schema_version` field
(Sprint 064 T001, ADR-0038 §2). `schema_version` is serialized by `to_dict()`
and is therefore a material input to `compute_definition_hash`. Every
`definition_hash` recorded in a Signal Research run manifest persisted before
this change was computed from a payload that had no `schema_version` key.
Re-serializing the same logical study today produces a different
`definition_hash`, even though nothing about the study itself changed.

### Reason

The alternative — excluding `schema_version` from the hash, or special-casing
its absence in the hash computation to preserve old values — would make the
hash silently blind to the one field whose entire purpose is signaling a
material format change. ADR-0038 §2 explicitly accepts the break rather than
special-casing it, on the grounds that a version bump is a material change by
construction.

### Consequences

- A tool or operator comparing a `definition_hash` recorded before
  2026-09-14 against one computed today for what they believe is the same
  study will see a mismatch that does not reflect any change to the study's
  actual configuration.
- `run_id` is unaffected — it derives from `derive_run_id_v2`'s material-input
  tuple, not from `definition_hash` — so historical runs remain discoverable
  and comparable by identity; only the configuration-fingerprint's meaning
  changed.
- A repository scan at Sprint 064 Wave 0 (2026-09-14) found no committed
  `SignalResearchDefinitionSpec` YAML files under `apps/cli/examples/` or
  `configs/`; the practical affected surface is test fixtures, documentation
  examples, and any operator's uncommitted `user_data/` files.

### Safe Operating Boundary

No workflow or tool may treat a `definition_hash` mismatch across the
2026-09-14 boundary as evidence of a configuration change without also
checking `schema_version` on both sides. Past run manifests are immutable and
must never be rewritten, backfilled, or migrated to a recomputed
`definition_hash` — not by a script, not by the workbench, not by a
"one-time fix".

### Repayment Trigger

An operator or tool is observed comparing hashes across the boundary and
drawing an incorrect conclusion from the mismatch. Absent that, this debt is
expected to age out on its own as pre-Sprint-064 manifests become
historical.

### Repayment Direction

Not prescribed here. If repayment is ever warranted, it likely means
documenting the boundary date alongside affected manifests, or a
tooling-level guard that refuses a raw hash comparison without also checking
`schema_version` — not a retroactive rewrite of historical hashes, which
ADR-0038 §2 already rejected.
