## TD-035 — Trusted Local Model Lineage Hash Covers Only the Entry File

```text
Status: ACCEPTED
Priority: LOW
Domain: apps/workbench (model discovery) / Models / Strategy
Introduced: Architecture triage of docs/product/PRD-research-workbench-mvp.md
  (ADR-0039), 2026-09-14
Target Review: Before promoting workbench-discovered local models beyond the
  MVP's read-only catalog, or if a drifted sibling import is observed causing
  a mismatched research result
Owner: Unassigned
```

### Accepted Shortcut

ADR-0039's trusted local model discovery computes a lineage hash from the
content of the declared entry file only (`market_model_file` /
`signal_model_file`, per ADR-0027's `build_strategy()` contract). A model's
entry file commonly imports sibling modules in the same user directory; none
of those are covered by the hash.

### Reason

Hashing a full dependency closure would require either statically resolving
Python imports (fragile, and itself a form of executing/interpreting
untrusted code paths) or importing the module during a read-only catalog
scan — the exact behavior ADR-0039 rejects to avoid weakening the existing
trusted-code warning and to keep discovery side-effect-free. Entry-file-only
hashing was accepted as the smallest correct mechanism that satisfies
ADR-0039's constraint.

### Consequences

- Two catalog entries can show the same lineage hash while a sibling module
  the entry file imports has changed, silently changing runtime behavior
  without a visible identity change in the workbench catalog.
- A user editing a shared helper module used by several local models will not
  see any of those models' lineage hashes change.

### Safe Operating Boundary

The lineage hash is a discovery-time convenience identity, not a
reproducibility guarantee. No workflow may treat two equal lineage hashes as
proof of identical execution behavior when the model's entry file imports
sibling modules. This does not change ADR-0027's existing trusted-code
warning, which remains the operative safety boundary at execution time.

### Repayment Trigger

A workbench increment that promotes local models into a run comparison or
lineage-sensitive feature where a silently drifted sibling import would
produce a misleading result, or a maintainer-observed case of exactly that
drift.

### Repayment Direction

Not prescribed here. A future repayment would need to choose between a
bounded static import-graph hash (same directory, non-recursive into
site-packages) or accepting the limitation permanently with clearer UI
disclosure — a design decision for the increment that repays this.
