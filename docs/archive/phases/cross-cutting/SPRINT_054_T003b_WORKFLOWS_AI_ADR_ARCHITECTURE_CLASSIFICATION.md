
# Sprint 054 T003b — `WORKFLOWS_AI_ADR.md` §1–§5/§8 Section Classification

## Methodology and scope

This artifact is the read-only classification output required by Sprint 054
T003b (`docs/planning/sprints/SPRINT_054.md`), applying the same four-way
classification framework established by
`docs/historical/REPO_WORKFLOW_DOCS_AUDIT.md` Phase 6b (CURRENT / FUTURE /
MIXED / AMBIGUOUS) and used by T001–T003
(`SPRINT_054_T001_ARCHITECTURE_FOUNDATIONS_CLASSIFICATION.md`,
`SPRINT_054_T002_ARCHITECTURE_TECHNICAL_CLASSIFICATION.md`,
`SPRINT_054_T003_MULTITIMEFRAME_MARKET_MODEL_CLASSIFICATION.md`) to every
major section and numbered subsection of `docs/vision/WORKFLOWS_AI_ADR.md`
**§1–§5 and §8 only** — lines 1–1577 and 2542–2584 (~1,620 lines), read in
full.

**§6 "AI Agent Contract" (lines 1579–2167) and §7 "Architectural Decision
Records" (lines 2170–2540) are explicitly out of scope for this task.** They
are handled by separate tasks T006b (§6 → `AGENTS.md` /
`.cursor/rules/ARCHITECTURE_CONTROL.md`) and T006a (§7 →
`docs/adr/README.md`), per the accepted recommendation in
`SPRINT_054_T006_WORKFLOWS_AI_ADR_RECOMMENDATION.md`. This document does not
classify or evaluate those two sections at all.

For each section in scope, classification was based on:
1. the section's own framing language (normative "must"/"should"/"suggested"
   vs. descriptive claims of built behavior), and
2. a targeted code verification pass — `Grep`/`Read` in
   `src/trading_framework/` for the concrete types, enums, fields and
   modules the section names (e.g. `ResearchScope`, `SignalOccurrence`,
   `ExecutionMode`, `StrategyModelDefinition`, `OrderStatus`,
   `SimulationAssumptions`, `FamilyExperimentPlan`, `ExecutionEventType`).

Per **D-S054-02**, sections that could not be confidently classified from a
reasonable amount of reading + grep-level verification are marked
**AMBIGUOUS** rather than guessed as CURRENT. No content in
`WORKFLOWS_AI_ADR.md` was moved, edited, or rewritten to produce this table;
the actual move (if any) is **T006c**, gated on this classification being
reviewed.

Purely navigational/meta headers (numbered section-group headers with no
independent normative content, e.g. `# 3. Signal Research` itself as
distinct from `## 3.1 Purpose`) are marked **N/A (meta)**, matching
T001–T003's precedent. "…Rules" subsections that are pure restatements of
already-classified content in the same section (§3.17, §4.21, §5.16) are
classified by inheritance from the rules they restate, not re-verified from
scratch line by line.

## Notable findings

- **The T006 recommendation's five sampled sections all confirm CURRENT,
  with more nuance than the sample suggested.** §3.3 Research Scope
  (`ResearchScope` enum matches near-verbatim), §3.9 SignalOccurrence
  (`strategy/signal_occurrence.py` matches closely but not field-identical),
  §3.16/§4.20 on-disk layout (AMBIGUOUS — out of `src/`-grep scope, a
  `user_data/` workspace convention, not a code contract), §4.9 Batch vs
  Replay split (MIXED — Backtest side fully built, Replay side entirely
  absent), and §5.7 Order Lifecycle (MIXED — a real but much narrower
  3-state `DRY_RUN` lifecycle, not the full 8-state normalized one). The
  recommendation's "this reads as architecture" judgment holds; the finer
  current-vs-future split required the same subsection-level treatment
  T001–T003 already established as necessary.
- **Strategy Execution (§5) is the most FUTURE-heavy section of the entire
  file.** §5.11 Broker Abstraction, §5.12 Reconciliation, and §5.13 Recovery
  are all confidently FUTURE with zero code counterpart, and they are
  mutually reinforcing negative results (no broker to reconcile against, no
  reconciliation to recover from). This directly extends T001's and T002's
  independent finding that only `ExecutionMode.DRY_RUN` is supported —
  §5 shows *why*: the runtime that exists today is a closed-loop, single
  simulated-broker system with no external-facing broker adapter layer at
  all, not a partially-implemented multi-broker abstraction.
- **Strategy Research (§4) has a clear, previously undocumented asymmetry
  with Signal Research (§3): "family" and bounded multi-dimension research-space
  machinery exists richly for Signal Research (`family_planning.py`,
  `signal_research_family.py`) but has no counterpart for Strategy Research**
  (§4.5 Strategy Research Space, §4.14 Strategy Families, §4.18 Multiple
  Testing all found this gap independently). A future T006c/T009-adjacent
  follow-up (not this task) might flag this as a genuine architecture gap
  worth a problem-registry entry, since §4.5's `experiments:` YAML example
  is presented as already-working syntax but has no implementing module.
- **§5.6's Event-Driven Runtime section is the clearest confirmation that
  the top-level `events/` package is an empty stub**, independently matching
  T002's finding for `ARCHITECTURE_TECHNICAL.md` §8 (Event System). What
  exists instead (`execution/models/events.py`'s `ExecutionEventType`) is a
  persisted-fact enum with different names than the vision doc's suggested
  event types, not a routed pub/sub `EventBus`.
- **§3's Signal Research architecture is essentially fully CURRENT** — of
  its 17 subsections, 14 are CURRENT (several near-verbatim), with only
  §3.12 (a subset of planner telemetry fields), §3.14 (two analytics gaps),
  and §3.16 (out-of-scope storage convention) not cleanly CURRENT. This is
  the strongest evidence in the whole file for the T006 recommendation's
  headline claim that this document is target architecture, already
  substantially built — not aspirational process text.
